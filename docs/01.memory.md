## 架构关键决策（2026-09-08 实测校正）

0. **网页 Chat Thread 删除策略（2026-09-15，v0.2.3）**：deep.api 有 5 条路径调 `/chat_session/delete`（TTL 淘汰/LRU 池淘汰/失败销毁 fail()/rebuild 弃旧/auth 登录探测）——全是 spec §4.3 既定设计；v0.1.107 前 deleteSession 是 no-op，之后才真删，用户发现 Spice 聊天中网页 thread 消失即这些路径所为。用户拍板：新增设置 `autoDeleteWebThreads`（popup 设置页「自动删除网页 Chat Thread」checkbox，**默认关**=淘汰/失败/重建只解除本地映射，网页会话保留；开启才真删），持久化在 `providers.deepseek`，`panel.setAutoDelete` 实时生效；auth 探测的自建会话不受此控（始终清理）。孤儿会话堆积是接受代价。

1. **认证来源**：chat.deepseek.com 的 localStorage `userToken`（格式 `{"value":"<JWT>","__version":"0"}`），由 MAIN world content script（bridge-main）读取推送，**不是 cookie**（user_token cookie 取不到）。
2. **token 推送**：只有 chat.deepseek.com 页面读 token 并推送 `auth.sync`（v0.1.106 起 `isAuthSyncHost` 严格匹配，不再 `*.deepseek.com` 通配——其他子域名残留的过期 userToken 会顶掉好 token，见教训条目）；其他网页只挂 `window.deepApi` 不推 null（否则 popup 登录态闪烁）。SW 收到 null token 且当前有有效 token 时**不清缓存**；采纳策略在 `src/background/auth-sync.ts`（坏名单+好窗口守卫，可单测）。
3. **DeepSeek API 头**：只带 `Authorization: Bearer <token>` + `Content-Type: application/json`；**X-Client-*、credentials:include（cookie）会触发 WAF 拦**（返回 SPA HTML/401）。
4. **URL 前缀**：SW fetch base = `https://chat.deepseek.com/api/v0`；adapter 内部路径**不带** `/api/v0`（如 `/chat_session/create`），拼双重前缀会返回 SPA HTML。
5. **响应包装**：session id 在 `data.biz_data.id`；PoW challenge 在 `data.biz_data.challenge`（不是 `data.chat_session.id`/`data.challenge`）。
6. **PoW（DeepSeekHashV1 wasm）调用约定**（对照 RezaParsian/DeepseekPowsolver 实测）：`wasm_solve(retptr, cPtr, cLen, pPtr, pLen, difficulty_f64)`；`__wbindgen_export_0` 是 `malloc(size, align)`（**2 参数**，align=1）；answer 读取是 **f64**（栈偏移 +8）；**status=1 成功、0 失败**；malloc 可能 realloc 内存，每次操作后重取 memory buffer 视图。prefix = `${salt}_${expire_at}_`（expire_at 毫秒）。
7. **SSE 事件格式**（实测）：`{"p":"response/content","o":"APPEND","v":"你好"}` 缩写（path/op/value）；连续增量 `{"v":"！"}` **省略 p/o（继承上式）**；内容路径是 `response/content` 不是 `response/fragments`；usage 是 `{"p":"response/accumulated_token_usage","o":"SET","v":66}`；ready 事件 `request_message_id`/`response_message_id` 在顶层。
8. **completion 请求体**：`{chat_session_id, parent_message_id, model_type, prompt(纯文本), ref_file_ids, thinking_enabled, search_enabled, preempt}`；prompt 是**当前轮用户消息纯文本**（不写 `<｜user｜>` 模板，网页端会显示）；多轮靠 parent_message_id 链。
9. **多轮增量**：调用方必须传**完整 messages 数组**（含历史 user + assistant 回复，仿 OpenAI SDK 行为）。SessionMapper mirror 必须含 assistant 回复（`commit` 时并入 `messages + {role:'assistant', content: agg.content}`），否则下一轮 tail 以 assistant 开头被判 rebuild → 新建会话 → 上下文丢失。**服务端靠 `parent_message_id` 关联历史**（参考 zhu1090093659/deepseek-pp 实测：body 只含 `prompt: string` 单字段 + `parent_message_id`，多轮不拼全量 messages 到 prompt）。v0.1.39 加 `action: null` 字段与 reference 对齐（增量保障）。
10. **popup 心跳**：只向 SW 请求完整 state（`panel.getState`，2s 一次），不直读 storage。
11. **storage 读取**：用数组形式 `chrome.storage.local.get([key])`（单字符串 key 的 await 返回形状不稳定，丢字段）。
12. **CSP**：MV3 默认禁 wasm，manifest 需 `content_security_policy.extension_pages` 加 `'wasm-unsafe-eval'`。
13. **demo 页 = Debug 仪表盘**（v0.1.66）：`src/debug/demo-page/` 不再是「6 场景按钮」，改为 5 tab（Chat / 路由 / 日志 / SSE 帧 / 场景）。`SessionMapper.listThreads()` 新增聚合 `log.list()` 中最近一次 cid 的 action；`RingLog` 容量 200→500；新增 `panel.listThreads` 面板消息（沿用 sw.ts:340 `panel.listLogs`）。`panel-api.ts` 用单例 port 共享避免反复 connect。rebuild 按钮保留在「场景」tab——它是 `decide()` 已实现路由分支的真实演示入口，不是 v1 没实现的功能（v1 没实现的是 edit_message 端点，参考本文件「运行时编辑已发送消息」条目）。

## 经验教训

- **日志双按钮与去重设计（2026-09-15，v0.2.4）**：「复制 (尾5条)」（原「复制取证」，白名单取证贴 AI）与「复制(全部)」（原「复制」）是不同受众、相反尺寸约束，不合并（用户拍板保留双按钮）。重复数据两源：messagesFull 每条带全量历史（O(N²)）+ mirrorFull ≈ 本轮 messages。修法：`slimFullCopy` 在复制层去重（mirrorFull 全排除；messagesFull 仅每 cid 末条；无 cid 条目各算一组），不动 LogEntry 写入（debug 页每条完整 JSON 不受影响）；新增 `lastUserSample`（最后一条 user 前 200 字）；popup 日志列表渲染 `req=`/`user=` 行（requestFull 早已含 reasoning/search，只是 UI 此前不显示）。

- **token 多来源交替推送 → SW 缓存反复翻转 → 调用定期 401/40003**（2026-09-15，v0.1.106 修复）：bridge-main 曾在所有 `*.deepseek.com` 页面每 5s 推本页 localStorage 的 userToken；www 等子域名残留的过期 token 与 chat 站好 token 互相顶替，SW 缓存每 ~5s 翻转一次，坏半周期内全部请求登录失效。修法：① `isAuthSyncHost` 只认 `chat.deepseek.com`（`bridge-main.ts`）；② SW 采纳策略收拢 `auth-sync.ts`：坏名单（10min 内探测 expired 的 token 直接拒，不重复探测）+ 好窗口（缓存 10min 内 logged_in 时 incoming 先探测，expired 不顶替），窗口过期回退照实采纳。教训：**fire-and-forget 的多来源状态同步必须有来源白名单**，"变了就收"在多写方下必然振荡。
- **扩展重载后老页面必报 Extension context invalidated，属预期，不是安装坏**（2026-09-15，v0.1.107 处理）：重载/更新扩展会销毁旧上下文，已开页面里驻留的旧 bridge-relay 调 connect 必拋此错；刷新页面重新注入即恢复。旧 relay 对它照常退避重试 → 每个老标签页永久刷错（1s→30s 退避）。修法：`isContextInvalidated`（`chrome.runtime.id` 缺失为可靠信号 + 报错文案兑底）命中即终态停机，只打一条 "refresh this page" 提示；其余失败照旧重试（旧测试曾拿该错误文案当通用失败错误，已改用非终态文案）。教训：**终态失败与瞬态失败必须分类**，退避重试只适用于后者。
- **vision 轮询超时 = 继续发 + warning 日志，不是报错**（2026-09-11 定稿）：参考实现 llmweb2api `client.ts:pollFileReady` 超时只 log 后返回（不抛）；旧 spec 写的「408 / 必须显式报」与参考不符，已改 `docs/superpowers/specs/2026-09-09-vision-multimodal-design.md` §3.3/§4.1。实现：窗口 10×2s=20s（曾缩到 5×1.5s 是为绕开 poll URL 双前缀 bug，已修），超时 `pollFileReady` 返回 `{ready:false}`，router 写 `LogEntry.warnings`（debug 日志 tab 可见）后带 ref_file_ids 发 completion；文件 FAILED / 上传被拒等请求侧失败仍显式报 400，可重试类（401/429/WAF/网络）映射 503/429。

- **DeepSeek 网页断流信号 + 续接端点**（2026-09-11 实测，v0.2.2 部分落实）：生成中途断流时 wire 上是 `response/status=INCOMPLETE` + `{"type":"error","content":"Server is temporarily unavailable.","finish_reason":"generation_err"}`（另有 `response` 的 BATCH 帧携带 `accumulated_token_usage` 与 `quasi_status`）。旧 parser 把 error 帧当 unknown 丢弃 → 空回复判 `finish_reason:stop`（silent bug）；v0.2.2 识别 error 帧/非 FINISHED 终态 → `stream_error` 事件 → Router 抛 503（分块已发的部分不回滚），并解包 BATCH。**自动续接端点实测**：`POST /api/v0/chat/continue` body `{chat_session_id, message_id, fallback_to_resume:true}`（message_id=截断的 assistant message；**无 PoW 头**、无 prompt/model_type/parent_message_id）。**`auto_resume:false` 时网页仍显示 Continue 按钮**——勿据该字段推断 UI 行为（曾误判，用户网页实测纠正）。续接响应流抓包与自动续接设计见 `docs/02.todo.md`。
- **stream:true 返回值形状必须严格遵循 OpenAI Chat Completions SSE 契约**（v0.1.49 修复）：必须是 `Response-like`（含 `body.getReader()`，content-type: text/event-stream），不是 `AsyncIterable<string>`。下斴（如 spice `parseDeepApiSse`）用 `body.getReader().read()` 读 Uint8Array + TextDecoder 拼 SSE 帧。`AsyncIterable<string>` 返了会被判定非 Response，fall back 到按 `{choices:[...]}` 形状取数据取不到 → 空响应 → 「AI 无回复」。v0.1.45 改 SSE 帧序列化到 `AsyncIterable<string>`，v0.1.49 才改成 `Response`，中间四版接口形状不匹配是 bridge 侧历史 regression。
- **构建输出目录：extension/**（v0.1.49 决定，取代 dist/）。Chrome 直接加载 `extension/`（manifest.json + sw.js + bridge-*.js + popup.* + demo/）。`build.mjs` esbuild outfile 与 copy 路径全走 `extension/`；`.gitignore` 忽略 `extension/`（构建产物不入仓，用户 git pull 后跑 `bun run build` 再加载）。历史：项目曾用 dist/，用户实际加载 extension/ 路径，两边混淆 v0.1.49 回归单一目录。如果以后加 CI 发版脚本，发布产物路径同步为 `extension/`。
- **模型输出工具调用的形态不确定**（实测至少三种）：标签（含缺左尖括号变体）；代码块包裹的 JSON（[ ]）；**裸 JSON 对象/数组**（整个 content 就是工具调用 JSON，无任何包裹——v0.1.33 用户实测发现）。parseToolCalls 必须三层 fallback 才能稳。
- **DeepSeek 业务响应码**：HTTP 200 + 业务 code 非 0 是常见 token 过期形态。`fetchJson` 必须同时检查 HTTP 状态**和**业务 code，否则会把登录失效误报成误导性的 `id missing`（v0.1.32 修复）。
- **Prompt 工程式工具调用局限**：模型在 `tool_choice:auto` 下**不保证**调用工具（实测有时直接文本回答）。要稳定强制调用需 OpenAI 的 `tool_choice:'required'`（当前未实现）。
- **Thinking / reasoning_effort 默认值**（v0.1.35 修正 → v0.1.72 误判 → v0.1.79 回滚 → **v0.2.0 重构字段**）：与 DeepSeek 官方文档对齐——thinking 默认 enabled、reasoning_effort 默认 high，**所有模型（flash/pro/vision）默认 thinking=true**。v0.1.72 曾把 Pro 改为 false——当时误判「thinking_enabled=true 让 Pro 只思考不说话」，实际根因是 v0.1.75-78 修的三件套（客户端版本头缺失/嵌套快照未解析/APPEND 数组未处理），与 thinking 无关；v0.1.79 回滚为 true。调用方显式传 `reasoning: 'off'|'minimal'|...|'max'` 覆盖（v0.2.0 起——见下条）。
- **调用方开关**（v0.1.34 → **v0.2.0 硬切到 pi-ai 对齐**）：v0.2.0 起请求可传 `reasoning: 'off' | 'minimal' | 'low' | 'medium' | 'high' | 'xhigh' | 'max'`（pi-ai `ModelThinkingLevel` 命名）+ `search: boolean`。**硬切**（无 alias 无 deprecation），老 `thinking: bool | null` + `reasoning_effort: 'low'|'medium'|'high'|'max'` 两字段契约废止。映射表见 `docs/superpowers/specs/2026-09-11-reasoning-search-field-alignment.md` §3.2。
- **v0.2.0 公开 API 破坏性变更**（feat/reasoning-search-alignment）：为对齐 pi-ai SDK 减少跨 provider 学习成本（DeepSeek/Gemini/ChatGPT 统一抽象），硬切原两字段（`thinking` + `reasoning_effort`）为单字段 `reasoning: ModelThinkingLevel`；版本跳 patch → minor（0.1.107 → 0.2.0）。**调用方唯一外部用户是 spice**，同步升级。**验证三步**：(1) tsc 0 错误（v0.1.83 教训）；(2) `bun run test` 全绿（11 个新 completionPayload 映射用例 + 3 个新 chat UI 用例）；(3) `extension/sw.js` bundle 里看 `r==="off"||(r===void 0?(i.thinking_enabled=t.thinking,i.reasoning_effort="high"):...)`（`completionPayload` minify 后字面）。后续若要加 `samplingParams`/`providerOptions` 透传容器，等接第二家 provider 时再抽。
- **网页 web API 的 thinking 响应层不分离**（v0.1.35 实测 → **v0.2.0 收紧措辞**）：原 v0.1.35 条目说「thinking 字段是 no-op」不准——网页 UI 上 Thinking 开关是真实有效的，请求层带 `thinking_enabled: true/false` 服务端会按指令决定是否进入推理模式（v0.2.0 实现仍照传），**只是响应层不单独拆分 `reasoning_content` 通道**：`chat.deepseek.com/api/v0/chat/completion` 的 SSE 流里**不返** `think_delta`，`message.reasoning_content` / `delta.reasoning_content` 始终为空；思考结果混在 `content` 里输出。增量 `reasoning_content` 只有官方 API（api.deepseek.com，需 API key）返。**调用方应按"可能没有 reasoning_content"写代码**；透传字段不报错（多余字段被服务端忽略）。`reasoning: 'off'` 的实现是字段缺席而非 `thinking_enabled: false`，与 pi-ai `thinkingLevelMap: {off: null}` 语义对齐。
- **tool_choice: 'required'**（v0.1.36）：ToolChoice 类型加 'required'；buildToolPrompt 生成强指令“必须调用至少一个工具”。是 prompt-engineered 强指令，模型可能不遵守（实测效果不如官方 API）。
- **demo 页**（v0.1.36）：`examples/demo-page/index.html` 提供 6 个场景 + thinking/search/reasoning_effort 控件 + vision 上传（实测型；网页 web API 对 image content 支持待验证）。**v0.1.40 修正 demo `runToolScenario`**：原代码第二轮 messages 漏了 user 追问"那明天呢？"，导致 `renderTail` 只取最后一条 tool 消息作为 prompt，模型看不到问题。修复后第二轮推送顺序：`assistant(tool_calls) → tool(result) → user(那明天呢？)`，与 OpenAI SDK 工具调用多轮调用一致。

- **Vision 未启用**（v0.1.37 实测确认 → v0.1.66 加强拒绝）：网页 web API 的 completion body `<code>prompt</code>` 是单字符串，**不**接受 OpenAI 风格 `<code>messages[].content</code>` 数组（含 `<code>image_url</code>` block）。v0.1.66 加 `router.create()` 入口校验：array content → 400 `invalid_request_error`，拒绝在 `createSession` 之前。**v1 该错误为预期结果**：vision 仍需独立上传端点 + `ref_file_ids`（v2 spike）。
- **模型中途切换会重开 session**（v0.1.67）：DeepSeek 网页 web API 一个 chat thread 不能中途换 `model_type`；复用旧 `webSessionId + parent_message_id` 链与新 model 不一致，行为未定义。`ThreadEntry` 跟踪 `modelType`，`decide()` 比对请求 vs 存储，不一致 → `rebuild`（deleteSession + createSession + `renderTranscript` 拼接完整历史作为 prompt）。老持久化 thread 无 `modelType` 字段 → 不约束，首轮 commit 后补上。
- **扩展加载后未 build = 加载了旧代码**（v0.1.66/v0.1.67 教训）：`§13` 合并主流程走完后必须跑 `bun run build` 将新代码打进 `extension/sw.js`，否则 Chrome 加载的 sw.js 还是上个版本的产物，manifest.json 的新版本号会误导以为修生效。**验证步骤**：合并 + bump 后跑 build → 检查 `extension/sw.js` 时间戳更新 → 检源里新增的关键字符串是否进 bundle（v0.1.66 的 `vision / image_url 暂不支持`、v0.1.67 的 `modelType` 记号）。下次 reload 不了记得按这三点核。
- **运行时编辑已发送消息**（v1 不实现）：deep.api 不支持改已发消息内容后“仍走同一 web session”——mirror 不匹配 → rebuild → 开新 session → 网页端看到两个 chat thread。DeepSeek 提供独立端点 `<code>POST /api/v0/chat/edit_message</code>`（body: `{chat_session_id, message_id, prompt, search_enabled?, thinking_enabled?}`，参考 nguyenduclong-ict/llmweb2api），但 v1 不接入。demo 页 rebuild 按钮明确说明这个行为是有意设计。v2 需要时再 spike：mapper 检测“被修改的消息索引 + 新内容”调 edit_message，让修改历史真正在同一 session 上生效。

- **DSML 是 DeepSeek V4 的原生工具协议**（2026-09-10，v0.1.102 定稿）：`<｜DSML｜tool_calls>` / `<｜DSML｜invoke name="X">` / `<｜DSML｜parameter name="K" string="true|false">`（全角 ｜ U+FF5C）。网页 API 下模型在长上下文（spice 13K prompt）会从 prompt 教的 `<tool_calls>` 回退到它。**网页 API 无 guided decoding（官方服务端有）→ 模型在自己学的分布上复现这个特殊标记，形态持续漂移**，已实测五种：小写/ASCII 竖线；闭标签无命名空间；开闭全无；**两侧各 2 竖线 + DSML 后多一空格 + 包裹名 `calls`（`tool_` 整段不在）**；**标准 `<tool_calls>` 开块 + 闭标签整体漂移**（`</｜｜DSML｜｜ …>`，`<` 与竖线间有 `/`，v0.2.5）。所以：开/闭标签命名空间可选、竖线 `[|｜]+`、容忍其后空白、接受 `calls`；且**检测判据刻意宽于解析判据**（开/闭标签均认：`</?`+竖线+`DSML`+竖线，v0.2.5 起含闭标签形态；解析仍严格），解析不出就走 repair/400，**绝不静默透传**（旧行为=原文当正文 + `finishReason=stop`，下游以为模型只是没调工具）。教训：**别照抄二手 tag，也别指望枚举形态收敛**——先查权威实现（vLLM parser / llama.cpp `common/parsers/deepseek.cpp` 的 `build_grammar`），它们把标记当字面量写死，现场必须自己容错并显式注释（偏差清单在 `dsml-parser.ts` 文件头 + spec §4.4）。
