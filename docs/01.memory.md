## 架构关键决策（2026-09-08 实测校正）

1. **认证来源**：chat.deepseek.com 的 localStorage `userToken`（格式 `{"value":"<JWT>","__version":"0"}`），由 MAIN world content script（bridge-main）读取推送，**不是 cookie**（user_token cookie 取不到）。
2. **token 推送**：只有 chat.deepseek.com（及 *.deepseek.com）页面读 token 并推送 `auth.sync`；其他网页只挂 `window.deepApi` 不推 null（否则 popup 登录态闪烁）。SW 收到 null token 且当前有有效 token 时**不清缓存**。
3. **DeepSeek API 头**：只带 `Authorization: Bearer <token>` + `Content-Type: application/json`；**X-Client-*、credentials:include（cookie）会触发 WAF 拦**（返回 SPA HTML/401）。
4. **URL 前缀**：SW fetch base = `https://chat.deepseek.com/api/v0`；adapter 内部路径**不带** `/api/v0`（如 `/chat_session/create`），拼双重前缀会返回 SPA HTML。
5. **响应包装**：session id 在 `data.biz_data.id`；PoW challenge 在 `data.biz_data.challenge`（不是 `data.chat_session.id`/`data.challenge`）。
6. **PoW（DeepSeekHashV1 wasm）调用约定**（对照 RezaParsian/DeepseekPowsolver 实测）：`wasm_solve(retptr, cPtr, cLen, pPtr, pLen, difficulty_f64)`；`__wbindgen_export_0` 是 `malloc(size, align)`（**2 参数**，align=1）；answer 读取是 **f64**（栈偏移 +8）；**status=1 成功、0 失败**；malloc 可能 realloc 内存，每次操作后重取 memory buffer 视图。prefix = `${salt}_${expire_at}_`（expire_at 毫秒）。
7. **SSE 事件格式**（实测）：`{"p":"response/content","o":"APPEND","v":"你好"}` 缩写（path/op/value）；连续增量 `{"v":"！"}` **省略 p/o（继承上式）**；内容路径是 `response/content` 不是 `response/fragments`；usage 是 `{"p":"response/accumulated_token_usage","o":"SET","v":66}`；ready 事件 `request_message_id`/`response_message_id` 在顶层。
8. **completion 请求体**：`{chat_session_id, parent_message_id, model_type, prompt(纯文本), ref_file_ids, thinking_enabled, search_enabled, preempt}`；prompt 是**当前轮用户消息纯文本**（不写 `<｜user｜>` 模板，网页端会显示）；多轮靠 parent_message_id 链。
9. **多轮增量**：调用方必须传**完整 messages 数组**（含历史 user + assistant 回复，仿 OpenAI SDK 行为）。SessionMapper mirror 必须含 assistant 回复（`commit` 时并入 `messages + {role:'assistant', content: agg.content}`），否则下一轮 tail 以 assistant 开头被判 rebuild → 新建会话 → 上下文丢失。**服务端靠 `parent_message_id` 关联历史**（参考 zhu1090093659/deepseek-pp 实测：body 只含 `prompt: string` 单字段 + `parent_message_id`，多轮不拼全量 messages 到 prompt）。v0.1.39 加 `action: null` 字段与 reference 对齐（增量保障）。
10. **popup 心跳**：只向 SW 请求完整 state（`panel.getState`，2s 一次），不直读 storage。
11. **storage 读取**：用数组形式 `chrome.storage.local.get([key])`（单字符串 key 的 await 返回形状不稳定，丢字段）。
12. **CSP**：MV3 默认禁 wasm，manifest 需 `content_security_policy.extension_pages` 加 `'wasm-unsafe-eval'`。
13. **demo 页 = Debug 仪表盘**（v0.1.66）：`src/demo/demo-page/` 不再是「6 场景按钮」，改为 5 tab（Chat / 路由 / 日志 / SSE 帧 / 场景）。`SessionMapper.listThreads()` 新增聚合 `log.list()` 中最近一次 cid 的 action；`RingLog` 容量 200→500；新增 `panel.listThreads` 面板消息（沿用 sw.ts:340 `panel.listLogs`）。`panel-api.ts` 用单例 port 共享避免反复 connect。rebuild 按钮保留在「场景」tab——它是 `decide()` 已实现路由分支的真实演示入口，不是 v1 没实现的功能（v1 没实现的是 edit_message 端点，参考本文件「运行时编辑已发送消息」条目）。

## 经验教训

- 扩展加载目录是 `/Users/xmli/me/code/deep.api/extension/`（构建产物），**不是仓库根目录**；载入前先在 chrome://extensions 移除旧版。
- 版本机制：每次改代码后 `npm run bump`（x.y.z → x.y.(z+1)），构建流程见 README。
- SW 环境 console.log 要打开"Service Worker"链接才能看到；页面 console 只有 bridge-main 日志。
- deep.api 当前版本：v0.1.49（2026-09-09）。
- **stream:true 返回值形状必须严格遵循 OpenAI Chat Completions SSE 契约**（v0.1.49 修复）：必须是 `Response-like`（含 `body.getReader()`，content-type: text/event-stream），不是 `AsyncIterable<string>`。下斴（如 spice `parseDeepApiSse`）用 `body.getReader().read()` 读 Uint8Array + TextDecoder 拼 SSE 帧。`AsyncIterable<string>` 返了会被判定非 Response，fall back 到按 `{choices:[...]}` 形状取数据取不到 → 空响应 → 「AI 无回复」。v0.1.45 改 SSE 帧序列化到 `AsyncIterable<string>`，v0.1.49 才改成 `Response`，中间四版接口形状不匹配是 bridge 侧历史 regression。
- **构建输出目录：extension/**（v0.1.49 决定，取代 dist/）。Chrome 直接加载 `extension/`（manifest.json + sw.js + bridge-*.js + popup.* + demo/）。`build.mjs` esbuild outfile 与 copy 路径全走 `extension/`；`.gitignore` 忽略 `extension/`（构建产物不入仓，用户 git pull 后跑 `npm run build` 再加载）。历史：项目曾用 dist/，用户实际加载 extension/ 路径，两边混淆 v0.1.49 回归单一目录。如果以后加 CI 发版脚本，发布产物路径同步为 `extension/`。
- **模型输出工具调用的形态不确定**（实测至少三种）：标签（含缺左尖括号变体）；代码块包裹的 JSON（[ ]）；**裸 JSON 对象/数组**（整个 content 就是工具调用 JSON，无任何包裹——v0.1.33 用户实测发现）。parseToolCalls 必须三层 fallback 才能稳。
- **DeepSeek 业务响应码**：HTTP 200 + 业务 code 非 0 是常见 token 过期形态。`fetchJson` 必须同时检查 HTTP 状态**和**业务 code，否则会把登录失效误报成误导性的 `id missing`（v0.1.32 修复）。
- **Prompt 工程式工具调用局限**：模型在 `tool_choice:auto` 下**不保证**调用工具（实测有时直接文本回答）。要稳定强制调用需 OpenAI 的 `tool_choice:'required'`（当前未实现）。
- **Thinking / reasoning_effort 默认值**（v0.1.35 修正 → v0.1.72 收紧）：与 DeepSeek 官方文档对齐，官方 API 上 thinking 默认 enabled、reasoning_effort 默认 high。但 v0.1.35 结论「所有模型默认 thinking=true」只对 Flash 测过——**Pro（model_type=expert）在 chat.deepseek.com/api/v0 上 thinking_enabled=true 会进入「只思考不说话」路径**（sseBytes≈320 仅返 ready+遥测，0 content 0 thinking，B-3 现场）。v0.1.72 收紧：**Flash / vision 默认 thinking=true，Pro 默认 thinking=false** 走直答路径。调用方显式传 `thinking: true | null | false` 覆盖。`reasoning_effort: 'low'|'medium'|'max'` 覆盖（官方 medium/xhigh 都映射到 high）。网页 web API 上 thinking 字段对 Flash 仍是 no-op（v0.1.35）。
- **调用方开关**（v0.1.34）：请求可传 `thinking: bool | null`、`search: bool`、`reasoning_effort: 'low'|'medium'|'high'|'max'`。
- **网页 web API 的 thinking 字段是 no-op**（v0.1.35 实测确认）：`thinking_enabled:true` / `false` / `reasoning_effort` 在 `chat.deepseek.com/api/v0/chat/completion` 上**不影响响应**——SSE 流里**没有任何 think_delta**，`message.reasoning_content` / `delta.reasoning_content` 始终为空。思考增量只在**官方 API**（api.deepseek.com，需 API key）返回。这是网页桥接层的根本限制。调用方应按“可能没有 reasoning”写代码；透传这些字段不报错（多余字段被忽略）。
- **tool_choice: 'required'**（v0.1.36）：ToolChoice 类型加 'required'；buildToolPrompt 生成强指令“必须调用至少一个工具”。是 prompt-engineered 强指令，模型可能不遵守（实测效果不如官方 API）。
- **demo 页**（v0.1.36）：`examples/demo-page/index.html` 提供 6 个场景 + thinking/search/reasoning_effort 控件 + vision 上传（实测型；网页 web API 对 image content 支持待验证）。**v0.1.40 修正 demo `runToolScenario`**：原代码第二轮 messages 漏了 user 追问"那明天呢？"，导致 `renderTail` 只取最后一条 tool 消息作为 prompt，模型看不到问题。修复后第二轮推送顺序：`assistant(tool_calls) → tool(result) → user(那明天呢？)`，与 OpenAI SDK 工具调用多轮调用一致。

- **Vision 未启用**（v0.1.37 实测确认 → v0.1.66 加强拒绝）：网页 web API 的 completion body `<code>prompt</code>` 是单字符串，**不**接受 OpenAI 风格 `<code>messages[].content</code>` 数组（含 `<code>image_url</code>` block）。v0.1.66 加 `router.create()` 入口校验：array content → 400 `invalid_request_error`，拒绝在 `createSession` 之前。**v1 该错误为预期结果**：vision 仍需独立上传端点 + `ref_file_ids`（v2 spike）。
- **模型中途切换会重开 session**（v0.1.67）：DeepSeek 网页 web API 一个 chat thread 不能中途换 `model_type`；复用旧 `webSessionId + parent_message_id` 链与新 model 不一致，行为未定义。`ThreadEntry` 跟踪 `modelType`，`decide()` 比对请求 vs 存储，不一致 → `rebuild`（deleteSession + createSession + `renderTranscript` 拼接完整历史作为 prompt）。老持久化 thread 无 `modelType` 字段 → 不约束，首轮 commit 后补上。
- **扩展加载后未 build = 加载了旧代码**（v0.1.66/v0.1.67 教训）：`§13` 合并主流程走完后必须跑 `npm run build` 将新代码打进 `extension/sw.js`，否则 Chrome 加载的 sw.js 还是上个版本的产物，manifest.json 的新版本号会误导以为修生效。**验证步骤**：合并 + bump 后跑 build → 检查 `extension/sw.js` 时间戳更新 → 检源里新增的关键字符串是否进 bundle（v0.1.66 的 `vision / image_url 暂不支持`、v0.1.67 的 `modelType` 记号）。下次 reload 不了记得按这三点核。
- **运行时编辑已发送消息**（v1 不实现）：deep.api 不支持改已发消息内容后“仍走同一 web session”——mirror 不匹配 → rebuild → 开新 session → 网页端看到两个 chat thread。DeepSeek 提供独立端点 `<code>POST /api/v0/chat/edit_message</code>`（body: `{chat_session_id, message_id, prompt, search_enabled?, thinking_enabled?}`，参考 nguyenduclong-ict/llmweb2api），但 v1 不接入。demo 页 rebuild 按钮明确说明这个行为是有意设计。v2 需要时再 spike：mapper 检测“被修改的消息索引 + 新内容”调 edit_message，让修改历史真正在同一 session 上生效。
- **SW port disconnected console error**（v0.1.62 修复）：`chrome.runtime.onConnect` 任意分支只要调 `port.postMessage`，必须套 `safePost`（`panelAlive` 哨兵 + try/catch）。v0.1.61 `deepapi` 分支做了、`deepapi-panel` 分支漏掉，导致 reload 扩展时 console 报 unhandled `Attempting to use a disconnected port object`。修法：在 onConnect 内 `let panelAlive = true; port.onDisconnect.addListener(() => { panelAlive = false; panelPorts.delete(port); }); const safePostPanel = (m) => { if (!panelAlive) return; try { port.postMessage(m); } catch { panelAlive = false; } };`，3 处裸 `postMessage` 全改 `safePostPanel`。教训：onConnect 多分支里只要有一处 postMessage 没护栏，reload 时 SW 必崩。
- **panel-api 单例 port 简化 in-flight 队列**：v0.1.66 debug 页 tab 内部不会并发 listLogs/listThreads（拉刷新串行），单 in-flight 队列够用；并发需求出现时升级到 seq 配对模式。
- **demo 页入口脚本链路是 plan Step 6/7/8 组合的隐性依赖**（v0.1.66 → v0.1.67 修）：`src/demo/demo-page/demo.js` 是入口脚本（import mountDebugPanel + `mountDebugPanel(document.getElementById('root'))`）。esbuild entry 必须是 `demo.js`（不是 `debug-panel.ts`），outfile 用 demo.js；`index.html` `<script src='demo.js'>`。**任一步错配 → root 永远空白、0 console error、jsdom 验证才能发现**——visual review 不能发现。debug-panel.ts 单独 IIFE bundle 没人调 mountDebugPanel 是这次回归的根因。**写 demo 改造 plan 时必须明确 esbuild entry = demo.js + index.html src = demo.js**，不能各 step 各自 OK 就当组合 OK。Next-time：plan 加 "jsdom verify root has children after build" 作为必跑验收（不依赖 Chrome 手动）。
- **commit message ≤72 字符 hard rule**（AGENTS.md §6）：本会话 3 次 commit 触发（Task 1 86 chars、entry-point fix 87 chars、chrome-shim fix 91 chars），都用 `git commit --amend` + `--force-with-lease` 修了——但 force-push main 破坏 history，CI/协作场景不安全。**Self-check 流程**：写 commit message 后先 `git log -1 --format='%s' | awk '{print length}'` 数长度，>72 立刻 amend 重新写短标题（正文 commit body 不限长度）。或用 `npm run lint-commit-msg` 类的 pre-commit hook（项目当前没有，未来加）。
- **demo 页 chrome-extension:// shim 是入口依赖**（v0.1.66 → v0.1.67 修）：`chrome-extension://.../demo/index.html` 加载路径（popup "Open Demo in new tab" 用 `chrome.runtime.getURL('demo/index.html')` 打开）下 content script bridge-main **不会注入** `window.deepApi`。v0.1.49 加的 shim（demo.js 顶部用 `chrome.runtime.connect({name: 'deepapi'})` 直连 SW 模拟 deepApi）是必须保留的入口脚本逻辑——Tab 实现（Chat/Scenarios）直接调 `window.deepApi.chat.completions.create` 假设它在所有页面都存在。Task 3 Step 6 改写 demo.js 极简化时把 shim 一起删了导致 model select 空、scenario 无法调。**Next plan**: 改 demo 任何入口脚本时都先检查 v0.1.49 self-shim 是否仍存在（git blame demo.js 看 4aefdf38 之前的版本）。
